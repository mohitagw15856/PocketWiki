# inkkit gaps

PocketWiki depends on [inkkit](https://github.com/mohitagw15856/inkkit) for the
device layer and deliberately does not reimplement anything inkkit already
provides (display framebuffer, SD storage and byte streaming, buttons, power).
This note records capabilities PocketWiki needed that inkkit does not currently
offer, so they can be considered for inkkit rather than worked around silently.

Where PocketWiki had to provide something itself, it did so in its **portable
core** (`core/pocketwiki/`) so the code is host tested and could move into inkkit
later with little change.

## 1. Text and glyph rendering

inkkit exposes the raw 1-bit framebuffer through `inkkit::Display` but provides
no font or text drawing. Each ecosystem firmware currently brings its own
(HabitInk a `FrameCanvas`, InkCards a `GfxRenderer`). PocketWiki added:

- `core/pocketwiki/Canvas.h`: pixel, rectangle and line drawing over the raw
  framebuffer.
- `core/pocketwiki/Font5x7.h`: a compact 5x7 bitmap font for printable ASCII,
  generated by `tools/genfont.py`.
- `core/pocketwiki/Text.h`: styled glyph drawing (bold, italic, integer scale),
  width measurement and word wrapping.

A shared, minimal text renderer would be a strong candidate for inkkit, since
every firmware with an on device UI needs one. inkkit already hints at this: its
`Display.h` notes a future on device InkCards UI sharing the panel plumbing.

## 2. On screen keyboard

inkkit has no text entry widget. CrossPoint relies on a keyboard component from
its own SDK layer. PocketWiki implemented a button driven grid keyboard in
`src/ui/Keyboard.h` (portable and host tested). A reusable keyboard widget would
belong naturally alongside a shared renderer in inkkit.

## 3. Selectable list and menu widget

Similarly, the paged, scrollable, selectable list used across most screens lives
in `src/ui/ListMenu.h`. It is generic and could be shared.

## 4. Directory listing shape

inkkit's `sd::listFiles(dir, ext, cb)` is sufficient for discovering `.pwa`
archives, and PocketWiki uses it as is. No gap here; noted only to confirm the
existing API met the need. inkkit's own `TODO(hardware-test)` on directory
iteration applies to us too and is tracked in `docs/HARDWARE_TESTING.md`.

## 5. Seekable SD reader

inkkit's `SdFileReader` (a `ByteReader` over a `HalFile`) is exactly what the
archive reader needs, and PocketWiki uses it unchanged. This is the model
dependency working as intended: the portable `PwaReader` takes an
`inkkit::ByteReader`, so it runs on the device over SD and on the host over an
`inkkit::MemoryReader` with no code changes.

## Summary

| Need | Provided by inkkit? | PocketWiki location |
| --- | --- | --- |
| Framebuffer access | Yes | `inkkit::Display` |
| SD byte streaming | Yes | `inkkit::SdFileReader` |
| Buttons, power | Yes | `inkkit::Buttons`, `inkkit::Power` |
| Text and font rendering | No | `core/pocketwiki/{Canvas,Font5x7,Text}.h` |
| On screen keyboard | No | `src/ui/Keyboard.h` |
| List and menu widget | No | `src/ui/ListMenu.h` |
